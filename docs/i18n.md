# 多语言开发

[文档首页](README.md) · [架构说明](architecture.md) · [开发指南](development.md)

界面使用 i18next + react-i18next。`src/i18n/locales/zh-CN.json` 与 `en.json` 是应用文案的唯一来源，随扩展离线打包，不请求翻译服务。现有 `ui.preferences.v1` 语言选择继续生效；默认简体中文，用户可选择 English。

## 界面与后台

React 组件通过 `useUi().t(key, params)` 渲染词条，避免把两种语言的句子内联在组件中。需要独立于 React 使用时，调用 `translator(locale)`。语言显式传入，后台任务不会修改其他页面的全局语言。

```ts
t('counts.pages', { count: 2 });
msg('task.joined', { name: group.name });
throw new AppError('error.http', { status: 403 });
```

后台、任务结果、诊断和确认框使用 `{ code, params }`，显示时由 `renderMessage` 解析。参数可以包含嵌套消息引用。任务记录保留消息码，切换语言后已经显示的状态、错误和确认框随之更新。用户输入、网页文本和第三方原始错误保持原文；字符串直接显示，不提供历史中文文案的查表翻译。

英文数量使用 i18next 的 `_one` / `_other` 词条与 `count` 参数，中文保持自然的计数格式。React 负责文本转义，不将翻译结果或插值送入 `innerHTML`。

## Chrome 原生文案

`scripts/build-locales.mjs` 从 `extension.*` 词条生成 `public/_locales/en/messages.json` 和 `zh_CN/messages.json`；manifest 使用 `__MSG_*__` 与 `default_locale: zh_CN`。运行 `npm run i18n:build` 可单独生成，dev/build/zip 会自动生成。生成结果应随词条一起提交。

Chrome 扩展名称、简介和快捷键说明由浏览器语言决定，无法通过扩展内语言选择即时修改。扩展界面、右键菜单、工具栏提示和 AI 输出使用扩展内的语言选择。

## AI 输出与任务记录

所有发给模型的系统指令统一英文；用户可见的新组名、描述按任务开始时记录的 `outputLocale` 生成。切换语言不会重命名已有分组，也不会改变正在运行任务的 AI 输出语言。模型输入中的网页与用户分组信息保持原文。

任务只使用 `organizer.task.v3`；不读取、迁移或显示旧格式记录，不保留旧任务执行器。原有设置、密钥、分组说明和独立撤销日志继续使用原来的存储机制。

## 新增文案与验证

1. 同时在两份语言文件中增加稳定的语义键，保持插值参数一致。
2. 直接显示使用 `t`；跨后台、持久化或延后显示的提示使用 `msg` / `AppError`。
3. 原生文案变更后运行 `npm run i18n:build`。
4. 运行 `npm run check`，并检查 320px 窄侧栏、长英文、切换语言和已打开的弹窗。

`tests/i18n.test.ts` 检查键与参数一致性、复数、嵌套消息、RPC 错误及原生词条。`tests/prompt-language.test.ts` 用 mock 验证英文指令与中英文输出约束；所有模型测试不调用真实服务。

## 语言选择与并发

界面使用 `ui.preferences.v1` 中保存的语言，后台串行合并偏好补丁，避免主题与语言的并发修改互相覆盖。两个页面监听同一存储变化，既更新可见文字，也更新文档语言和标题；它们不改动模型配置修订号或未保存草稿。

长期保存的任务消息不预先翻译为某个语言的句子；新任务必须带 `outputLocale`，同会话恢复沿用该值。由此，界面状态可以即时切换语言，正在运行的 AI 生成任务仍保持启动时选定的输出语言。

## 消息和错误示例

```ts
const detail = msg('task.joined', { name: group.name });
const notification = msg('action.result', {
  action: msg('actions.organize-window'),
  message: detail,
});
renderMessage(notification, locale);
```

在后台使用 `AppError` 传递可翻译的应用错误，通过 `errorForDisplay` 生成 RPC 可序列化的消息。原始第三方错误可保留字符串；不要通过匹配中文句子决定业务逻辑，业务分支应判断消息码或明确的状态字段。

JSON 两份词条的键名和插值变量应一致。新增数量文案时使用 `count`，不要在组件中拼接英文单复数；用户组名作为插值传入，不能被当作翻译键或再次解析的模板。添加新的完整语言需要同步语言类型、偏好校验、界面选项、资源注册和原生语言包生成脚本。
